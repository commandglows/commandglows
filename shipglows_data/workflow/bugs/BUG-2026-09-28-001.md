# Bug Record: BUG-2026-09-28-001

## Summary

The dashboard audit found account-selection races, incomplete support recovery states and public purchase links inside an entitled customer's training journey. Local corrections and regression checks are implemented. The record remains `fixed-pending-verify`; this means implementation with passing automated retests awaiting interactive verification, not verified closure or delivery.

The user initially authorized local correction through independent agents and read-only inspection of the development/production wiring. They subsequently explicitly authorized adding the missing production Convex environment variable through the CLI, then requested a clearer development environment label. The narrowly authorized production and development configuration corrections are recorded below. No real account mutation, payment, notification, secret change, commit, push or code deployment was performed.

## Reproduction and expected behavior

Use synthetic accounts, mocked HTTP responses and `convex-test` fixtures. Reorder requests when selecting customers, lose a response after submitting an intervention, fail a detail refresh, open the missing-payment queue directly, and follow an entitled customer's training links. Inspect unavailable-session recovery and FR/EN route transitions.

Expected behavior: only the current requested account is displayed; server authority and environment determine mutation targets; uncertain or stale outcomes require rereading; confirmed success survives failed refresh; each support form owns its reason; private training stays private; draft content is excluded; recovery preserves privacy and route context.

## Environment wiring: initial inspection and authorized updates

Root agent inspection on 2026-09-28 confirmed separate deployment destinations:

- Doppler `dev` and Convex development target `gallant-yak-850`; the initially inspected backend environment was `sandbox`.
- Doppler `prd` and Vercel production target the distinct Convex deployment `elegant-mule-677.eu-west-1`.
- Vercel production has `SUITE_BRIDGE_ENVIRONMENT=production`.
- At the initial inspection, Doppler `prd` did not define that key, and the Convex production environment lookup also returned the key absent.

Deployment separation is confirmed configuration evidence. It does not establish row contents, authenticated production behavior or correct entitlement mutation in production. The local licence correction requires a valid backend runtime environment.

After that inspection, the user explicitly instructed: “ajoute ces var dans convex via la cli oui”. Under that authorization, the root agent ran `doppler run --project commandglows --config prd -- pnpm exec convex env set SUITE_BRIDGE_ENVIRONMENT production --prod`. The CLI confirmed success on production deployment `elegant-mule-677`; a subsequent `convex env get SUITE_BRIDGE_ENVIRONMENT --prod` returned `production`. The missing production Convex key is therefore corrected and reread. At that stage, a complementary `convex env get SUITE_BRIDGE_ENVIRONMENT` through Doppler `dev` confirmed `sandbox`, with no development setter yet run. Doppler `prd` remains unchanged; this configuration update did not deploy the local code patch.

The user then requested changing the confusing development label. Under that instruction, the root agent set Convex development `SUITE_BRIDGE_ENVIRONMENT=development` through the CLI on `gallant-yak-850`, then set the same value in Doppler `commandglows/dev`. Readbacks confirmed Convex `development`, Doppler `development`, and `CONVEX_DEPLOYMENT=dev:gallant-yak-850`. These are the current development configuration values; the earlier `sandbox` readback is historical. Production remains `production` as corrected above. The existing `commerceEnvironment` contract already accepts `development` and normalizes it internally to `sandbox`. Source inspection also confirmed `src/lib/suiteBridge.ts:resolveBridgeEnvironment` explicitly accepts `development`, `test` and `production`, but not `sandbox`; the development configuration label now aligns with that bridge contract. This is source-contract evidence, not authenticated runtime proof. No code change, entitlement data migration or deployment was performed for this label update.
